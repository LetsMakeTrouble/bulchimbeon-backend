# 01. 기능명세 (MVP PRD 마인드맵 전개)

> PRD 기능명세 마인드맵(1.1~6.3)을 백엔드 관점으로 전개한 문서.
> 각 기능의 상세 동작 조건은 `02-business-rules.md`, API 형태는 `05-api-contract.md` 참조.

## 1. 프로젝트 및 지식 베이스 관리

| ID | 기능 | 설명 | 백엔드 구현 포인트 |
| --- | --- | --- | --- |
| 1.1 | 프로젝트 생성 및 참여(초대 코드) | 프로젝트 생성 및 초대 코드 참여 흐름 | 생성자 = 담당자(answerer). 초대 코드 발급·재발급, 코드로 질문자(asker) 참여 |
| 1.2 | 문서 업로드 및 버전 상태 관리 | 문서 업로드와 활성 버전 전환 | MD/TXT/PDF/DOCX 업로드 → 파싱 → 청킹 → 임베딩. 재업로드 시 새 버전 저장(기존 버전 보존), 활성 버전 전환 API |
| 1.3 | 프로젝트 응답 지침(가드레일) 등록 | 응답 지침 등록 및 강제 확인 규칙 적용 | 프로젝트당 응답 지침 텍스트 저장, 모든 답변 생성 프롬프트에 주입 |
| 1.4 | AI 답변 기준 및 판단 가중치 설정 | 응답 지침·등급 임계값·가중치 저장 | 등급 임계값(`green_threshold`/`yellow_threshold`), 근거 점수 하한(`grounding_min`), 유사도 리스케일(`s_floor`/`s_ceil`), 근거 하한(`similarity_floor`), 재사용·유사 임계값(`reuse_threshold`/`similar_threshold`), 일일 LLM 호출 상한(`daily_llm_call_limit`) 등을 프로젝트 설정으로 저장 — **코드 하드코딩 금지** |
| 1.5 | 지식 원본 연동 및 동기화 관리 | Notion·GitHub 연결과 수동 동기화 | Notion 페이지/DB, GitHub 레포 경로 연결. 수동 동기화 트리거 → 변경분을 새 문서/버전으로 인제스트 |
| 1.6 | 방해금지 시간 및 브리핑 전달 설정 | 방해금지 시간대의 질문 묶음 전달 | 담당자별 DND 시간·브리핑 시각 설정(**타임존은 `users.timezone`이 단일 원천 — settings에 별도 키 없음**). DND 중 즉시 알림 차단 + 브리핑 배치 적재 |

## 3. 근거 검색 및 답변 생성

| ID | 기능 | 설명 | 백엔드 구현 포인트 |
| --- | --- | --- | --- |
| 3.1 | 프로젝트 범위 근거 검색(활성 버전 문서) *(원 PRD명: 문서+공식 Q&A — D24로 축소)* | 활성 버전 문서 청크 근거 검색 및 출처 반환 | 검색 범위 = `documents.status='active'` 문서의 **활성 버전 청크로 한정**(D24). `chunks`와 `official_qas`를 한 랭킹에 섞지 않는다. 공식 Q&A는 ② 재사용 검사의 `similar_official_qa` 첨부 경로로만 노출된다(→ 5.2). 프로젝트 외부 지식 검색 금지 |
| 3.2 | 근거 기반 답변 생성 및 스키마 검증 | 스키마 기반 답변 생성과 근거 없는 주장 제거 | 문장 단위 인용 강제 구조화 출력(JSON 스키마 검증, 재시도 2회 초과 시 🔴). 근거 없는 문장은 제거하고 남은 문장으로 발행한다 — **G의 분모(생성 시점 원본 문장 수)는 고정이라 프루닝해도 매칭률은 오르지 않는다**(`02 §1`) |

## 4. 신뢰 등급 분기 및 담당자 확인 워크플로

| ID | 기능 | 설명 | 백엔드 구현 포인트 |
| --- | --- | --- | --- |
| 4.1 | 매칭률 계산 및 초록·노랑·빨강 분기 | 매칭률 신호 계산 및 강제 빨강 검사 | 매칭률 = min(검색 점수 S, 근거 점수 G) — 산식은 `02 §1`. 강제 🔴 **4종**: 문서 충돌(`conflict`) / 근거 0건(`no_evidence`, top-1 `sim_raw < similarity_floor` 포함) / 스키마 검증 실패(`schema_failed`) / 일일 LLM 호출 한도 초과(`quota_exceeded`). 4종은 DND에서도 강등되지 않는다(`02 §6`). |
| 4.2 | 담당자 확인 카드 생성 및 인앱 확인 큐 | 확인 카드 생성 및 큐 정렬/열람 기록 | `green\|yellow\|red\|feedback\|doc_update\|failed` **6종 모두** 카드 생성. 단 (a) `green` 카드는 큐에만 적재하고 브리핑·알림에서 제외(룰 1·3), (b) **재사용 답변(`source='reused'`)은 등급이 🟢이어도 카드를 만들지 않는다**(D11), (c) `failed` 카드는 `answer_id=NULL`·`draft_answer=null`(D23). 큐 정렬: 승인 추천(맞았다 2건↑) → 긴급 → 오래된 순(`05 §7`). 카드 열람 시각 기록(지표용) |
| 4.3 | 승인·수정·반려 처리(중복 차단) | 승인/수정/반려 및 정정 알림 | 승인 → 확정 + 공식 Q&A 편입. 수정 → 확정 + 정정 알림(양쪽 언어) + 교훈 후보 추출. 반려 → 사유와 함께 질문자 전달. 동일 카드 중복 처리 차단(멱등) |

## 5. 알림, 이력, 공식 지식 환류

| ID | 기능 | 설명 | 백엔드 구현 포인트 |
| --- | --- | --- | --- |
| 5.1 | 질문자 확정·정정·반려 알림 | 인앱 알림함에서 확정/정정/반려 알림 확인 | 알림함 CRUD + SSE 실시간 이벤트. 읽음 처리 |
| 5.2 | 공식 Q&A 편입 및 재사용 | 공식 Q&A 생성 및 후속 질문에서 재사용 | 확정 시 자동 편입(한국어 확정 원문 + 영어 번역 쌍 + 질문 임베딩). 원시 코사인 ≥`reuse_threshold`는 **재사용 후보**일 뿐이며, **LLM 동일성 게이트(yes/no 1회)** 가 `yes`일 때만 재사용한다. `similar_threshold`~`reuse_threshold` 구간은 유사 확정 답변 첨부. 상세는 `02 §4`·`06 §2` ②. |
| 5.3 | 이벤트 로그 및 처리 이력 조회 | 이벤트/이력 타임라인 기록 및 조회 | 모든 상태 변화를 events 테이블에 기록, 질문/답변 단위 타임라인 조회 API. 지표 계산의 원천 |

## 범위 제외 (이번 MVP에서 하지 않는 것)

- 웹푸시/모바일 네이티브 푸시 (인앱 알림함 + SSE로 대체)
- 한↔영 외 언어 조합, 언어 자동 감지
- 복수 담당자 (다음 버전)
- 문화 톤 변환의 고도화(기본 톤 지침 수준만)
- 매칭률 임계값 자동 보정(수동 설정만, 실측 정확도 표기는 지표 API로 제공)
- 조직 간 중립지대 UI (백엔드 데이터 모델은 프로젝트 단위로 이미 중립)
