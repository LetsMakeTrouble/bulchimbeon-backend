# 02. 비즈니스 룰 — 동작의 최우선 기준

> 기획팀이 작성한 비즈니스 룰 원문을 구현 기준으로 정리한 문서.
> **다른 문서와 충돌하면 이 문서가 이긴다.** 각 룰 하단 `[구현 노트]`는 백엔드 구현 방식을 못 박는다.

---

## 1. 답변 등급 규칙

시스템은 모든 답변에 **매칭률(0~100)**을 계산하고, 그 값에 따라 세 등급으로 나눈다.

| 등급 | 매칭률 | 동작 |
| --- | --- | --- |
| 🟢 **즉답 (green)** | 80 이상 | 질문자에게 바로 답변 + 출처. 담당자에게 **즉시 알리지 않는다.** 다만 카드는 `reason=green`으로 확인 큐에 적재하되 **브리핑·알림 대상에서는 제외**한다. "맞았다" 2건이 쌓이면 그때 `recommend_approve`가 되어 브리핑 최상단에 올라간다(룰 3). |
| 🟡 **확인 대기 (yellow)** | 50 ~ 79 | 답변을 보여주되 "담당자 확인 전" 표시. 담당자에게는 아침 브리핑으로 전달. |
| 🔴 **보류 (red)** | 50 미만 | 답변을 내보내지 않는다. 질문을 영어로 번역·정리해 담당자에게 넘긴다. |

> 🟢 카드가 "적재되지만 보이지 않는" 이유: 큐가 최종 안전망이라는 룰 6의 원칙을 깨지 않으면서도, 담당자의 브리핑을 즉답 건으로 채우지 않기 위함이다. 재사용 답변은 예외로 카드 자체를 만들지 않는다(룰 4, D11).

**매칭률 계산 — 4단계**

```
① 원시 유사도  sim_raw = 1 - (embedding <=> query_vec)                       # pgvector는 "거리"를 반환
② 검색 점수    S = round(clamp((sim_raw - s_floor) / (s_ceil - s_floor), 0, 1) × 100)
③ 근거 점수    G = round(지지 문장 수 / 생성 시점 원본 문장 수 × 100)
④ 매칭률       matching_rate = min(S, G)
```

- **검색 점수(S)** — 질문과 가장 가까운 근거 청크의 원시 유사도를 `s_floor`~`s_ceil` 구간으로 **리스케일**한 0~100 값. 임베딩 모델마다 코사인 유사도의 분포 중심이 다르므로(`text-embedding-3-small`은 평균 0.4대) 원시값을 그대로 100배 하면 🟢에 영원히 도달하지 못한다. 리스케일이 이 스케일 차이를 흡수하므로 **80/50 등급 임계값은 모델이 바뀌어도 그대로 유지된다.**
- `s_floor` / `s_ceil`은 **`projects.settings` 값**이다. 기본값 `s_floor: 0.25`, `s_ceil: 0.679` — **M-1 게이트 실측 확정값**이다 (2026-08-07, 도출 근거는 `04 §3`).
- **근거 점수(G)** — 답변 문장 중 근거 문서가 실제로 뒷받침하는 문장의 비율. **분모는 항상 "생성 시점 원본 문장 수"로 고정**한다. 무근거 문장을 지워도 분모는 줄지 않으므로 **프루닝은 매칭률을 올리지 못한다.**
- **매칭률 = min(S, G)** — 문서를 잘 찾았어도 답변이 문서를 벗어났으면 낮게, 답변이 충실해도 문서가 빈약하면 낮게.
- `grounding_min`(60) 미달이면 근거 없는 문장을 지우고 발행한다. 이는 **발행 품질을 위한 조치일 뿐 매칭률을 되돌리지 않는다**(분모가 고정이므로). 지우고 남는 내용이 없으면 🔴 보류.
- `grounding_min`은 **문장이 3개 이상일 때만** 적용한다. **1~2문장 답변은 전 문장이 supported여야 하며, 하나라도 무근거면 🔴**이다(비율 통계가 의미를 갖지 못하는 구간).

**강제 🔴 규칙 (매칭률과 무관하게 보류)**
1. 근거 청크 0건 (검색 결과 없음) — top-1 `sim_raw < similarity_floor`인 경우도 포함 · `no_evidence`
2. 문서 간 충돌 감지 (같은 질문에 상반된 근거) · `conflict`
3. 구조화 출력 스키마 검증 실패 (재시도 2회 소진) · `schema_failed`
4. **일일 LLM 호출 한도(`daily_llm_call_limit`) 초과** · `quota_exceeded`

> ⚙️ 80, 50, 60, `s_floor`, `s_ceil`, `similarity_floor`, `daily_llm_call_limit` 등 기준값은 코드에 박지 말고 **프로젝트 설정값**으로 둔다. (`projects.settings`)

**[구현 노트]**
- ⚠️ **pgvector의 `<=>`는 코사인 "거리"다** (SQLAlchemy 헬퍼명도 `cosine_distance()`). 유사도는 반드시 `1 - (embedding <=> :q)`로 만든다. 거리를 유사도로 착각하면 등급이 정확히 뒤집힌다.
- `S = round(clamp((sim_raw - s_floor) / (s_ceil - s_floor), 0, 1) × 100)`. `G = round(지지 문장 수 / 생성 시점 원본 문장 수 × 100)` — 분모는 프루닝 후에도 바뀌지 않는다.
- 재사용/유사 임계값(`reuse_threshold`, `similar_threshold`)은 **리스케일하지 않고 원시 코사인을 그대로** 쓴다(룰 4). S와는 다른 축이므로 섞지 않는다.
- 원시 유사도는 `answers.sim_raw`에 기록해 캘리브레이션 근거로 남긴다.
- 산출 파이프라인 상세는 `06-ai-pipeline.md` §2 ③·⑤·⑥(검색·S 리스케일 / 근거 검증·G 분모 고정 / 매칭률·등급·DND 강등), 검증 테스트는 `06 §5` 테스트 1~2.

## 2. 답변 생성 규칙

- 답변은 **근거 문서에 있는 내용으로만** 만든다. 문서에 없는 내용을 지어내지 않는다.
- 근거를 못 찾으면 일반 상식으로 답하지 않고 **보류** 처리한다.
- 담당자가 등록한 **응답 지침**과, 담당자가 승인한 **교훈**은 모든 답변 생성에 반영한다.

**[구현 노트]** 문장 단위 인용 강제(각 문장에 chunk id 배열) 구조화 출력. 인용 없는 문장은 G 계산 전에 표시되고 G<60 시 제거된다.

## 3. 답변 상태 규칙

상태: **참고(draft) → 확정(verified)**, 문제 발생 시 **재검토(under_review)**, 무처리 시 **만료(expired)**.

### 시작: 참고 (draft)
- 모든 답변(🟢 포함)은 **참고** 상태로 시작한다. 확정 전까지 "참고용, 미확정"임을 API 응답에 계속 표시한다. 유일한 예외는 **재사용 답변**이다 — 이미 확정된 원문을 그대로 내보내므로 `verified`로 시작하고 만료가 없다(룰 4, D11).
- 참고 상태로 **72시간** 동안 아무 처리가 없으면 **만료**시킨다. 단 **살아 있는 카드(pending·deferred)가 걸려 있는 답변은 만료시키지 않는다** — 담당자가 아직 처리 중인 건을 스위퍼가 밑에서 죽이면 안 된다(D14).
- **만료의 의미**는 두 가지다(D13): (1) 더 이상 **확정할 수 없다** — 승인·수정 대상에서 제외되고, 만료 답변의 카드를 처리하려 하면 409다. (2) 화면·API에 `expired`로 표기된다. 재사용 풀은 애초에 확정된 공식 Q&A뿐이므로 "만료 답변 재사용 금지"를 위한 별도 배제 로직은 필요 없다.

### 확정은 담당자만
- 담당자가 **승인하거나 수정해서 저장**하면 확정된다.
- 질문자는 확정할 수 없다. 질문자가 할 수 있는 건 **"맞았다(correct) / 달랐다(different)" 피드백**뿐이다.
  - 피드백은 **`draft` 또는 `verified` 상태에서만** 받는다. `expired`·`rejected`·`under_review` 답변에 피드백을 시도하면 **409 `FEEDBACK_NOT_ALLOWED`**다(D12).
  - **맞았다 2건 이상** 쌓인 답변은 담당자 브리핑 목록 맨 위에 **승인 추천**으로 올린다. 원탭 승인 가능. 그래도 **자동 확정은 없다**. 🟢 카드도 이때 비로소 브리핑에 등장한다(룰 1).
  - **달랐다** → 사유 한 줄 입력 → 답변을 **재검토** 상태로 전환 → 담당자에게 전달. 질문자 화면에는 답변을 지우지 않고 "오류 신고됨, 재검토 중" 표시를 덧붙인다.

### 재검토 처리 (담당자 택1)
- **수정해서 저장** → 확정 + 질문자에게 정정 알림(양쪽 언어).
- **원안 유지** → 확정 복귀 + 질문자에게 유지 사유 알림.

> ⚠️ **확정된 답변에도 "달랐다"를 누를 수 있다.** 이 경우에도 재검토로 전환된다. 해당 공식 Q&A는 재검토 해소 전까지 재사용을 멈춘다.

**[구현 노트]**
- 만료(expired)의 효과는 **확정 불가 + 상태 표기**다(D13). 질문자의 과거 조회 화면에서는 내용 유지 + `expired` 상태 표기.
- 만료 스위퍼 조건(D14): `state='draft' AND expires_at < now() AND 연결된 review_cards 중 status ∈ {pending, deferred}인 것이 없을 것`.
- 만료 전환은 스케줄러가 주기 실행(스위퍼). 72시간 값도 설정화.
- 피드백 허용 상태 검사는 서비스 계층에서 하고 위반 시 409 `FEEDBACK_NOT_ALLOWED`를 반환한다(D12). 피드백은 유저당 답변 1건이며 재제출도 409다.

## 4. 지식 재사용 규칙

- 새 질문 접수 시 **확정 답변(공식 Q&A) 검색을 먼저** 한다. 질문 유사도가 `reuse_threshold`(기본 **0.925**) 이상이면 같은 질문 **후보**로 본다.
- **재사용 2차 게이트** — 임계값 하나에 재사용을 걸지 않는다. 후보가 나오면 LLM에 *"이 두 질문은 같은 질문인가?"* 를 **yes/no로 1회** 물어 `yes`일 때만 재사용한다. `no`면 일반 생성 경로로 내려보내고 `answer.reuse_missed` 이벤트를 남긴다(룰 10의 분모).
- 게이트를 통과하면 **검색·생성 없이** 확정 답변을 바로 내보낸다.
- 유사도가 `similar_threshold`(기본 **0.855**) ~ `reuse_threshold` 구간이면 새 답변을 생성하되, "비슷한 확정 답변"을 함께 첨부한다.
- 확정 답변 재사용 시 **확정 당시의 한국어 원문을 그대로** 내보낸다. 영어 저장본을 재번역하지 않는다.

> ⚠️ `reuse_threshold` / `similar_threshold`는 **리스케일하지 않은 원시 코사인 유사도** 기준이다(룰 1의 S와 다른 축이다). 0.925·0.855는 **M-1 게이트 실측 확정값**이다 (2026-08-07).

**[구현 노트]**
- 재사용 응답은 `answer.source = "reused"` + `official_qa_id` 연결. 상태는 **`state=verified`, `expires_at=NULL`, 카드 미생성, 만료 스위퍼 대상 아님**(D11) — 담당자가 이미 확정한 원문이므로 다시 확정받을 대상이 없다.
- 등급은 🟢로 표기하되 매칭률 대신 "공식 확정 답변"을 표시한다(`matching_rate` 없음). `question.graded` 이벤트는 `grade=green, matching_rate=null, source=reused`로 발행한다.
- 재사용 답변에 "맞았다"가 들어오면 연결된 `official_qas.correct_count`를 증가시킨다(D22 — `answer.official_qa_id`가 있을 때).
- 공식 Q&A가 재검토로 내려가면 그것을 `official_qa_id`로 참조하는 `source='reused'` 답변도 함께 `under_review`로 내리고 질문자에게 알린다(D21).
- 재질문 즉답률 지표의 분자는 `answer.reused`, 분모는 `answer.reused + answer.reuse_missed`다(룰 10, D26).

## 5. 문서 갱신 규칙

- 문서를 다시 올리면 **새 버전**으로 저장한다. 기존 버전은 지우지 않는다.
- 새 버전이 **활성화되는 시점**에, 이전 버전을 근거로 확정된 답변(공식 Q&A 포함)을 전부 **재검토**로 내린다. 직후 담당자에게 "이 문서를 근거로 한 확정 답변 N건이 재검토 대상입니다" 알림을 보낸다.
- 담당자는 브리핑에서 해당 답변들을 묶음으로 보고 **전체 유지** 또는 **하나씩 재검토**할 수 있다.
- **문서를 삭제(soft delete)해도 같은 재검토 연쇄가 일어난다**(D20). 근거가 바뀌는 것과 근거가 사라지는 것은 답변 입장에서 동일한 사건이다. 파생된 공식 Q&A는 `archived`로 내린다.
- 교훈은 문서가 바뀌어도 자동 삭제하지 않는다. 대신 **재확인 필요(needs_recheck)** 표시를 붙인다.

**[구현 노트]**
- 업로드 시 기본 자동 활성화(`auto_activate=true` 기본값). 명시적으로 활성화를 미루면(기능 1.2) 재검토 연쇄도 활성 전환 시점까지 미뤄진다 — "업로드 직후" 룰과 "활성 버전 전환" 기능의 정합 해석.
- **근거 검색 대상은 `documents.status='active'` 문서의 활성 버전 청크로 한정**한다(D20). soft delete된 문서의 청크는 물리 삭제하지 않되 검색에서 빠진다.

## 6. 담당자 알림 규칙

- 보류 질문이라고 전부 즉시 알리지 않는다. 질문자가 **"급함(urgent)"을 표시한 경우에만 즉시 알림**, 나머지는 담당자 출근 시각에 맞춰 **아침 브리핑**으로 모아 보낸다.
- 급함 여부는 **질문자가 정한다**. AI는 질문에 마감·장애 표현이 있으면 "급한 질문인가요?" 제안 플래그만 반환할 수 있다.
- 담당자의 **방해 금지 시간(DND)**에는 어떤 즉시 알림도 보내지 않는다. 이 시간대의 🔴 질문 중 **매칭률 미달(`low_confidence`)로 보류된 건만** 🟡로 낮춰 추정 답변을 내보내고 브리핑으로 넘긴다.
- ⛔ **강제 🔴 4종(`conflict` / `no_evidence` / `schema_failed` / `quota_exceeded`)은 DND에서도 🔴을 유지한다.** 충돌 감지 결과나 근거 없음이 "몇 시에 물었는가"에 따라 조용히 은폐되는 것은 룰 2("근거 없으면 보류") 위반보다 심각하다. **강등 대상은 오직 `low_confidence`뿐이다.**
- **타임존 단일 원천** — 브리핑 시각과 DND 판정은 항상 **현재 담당자(`projects.answerer_id`)의 `users.timezone`**을 기준으로 한다. 프로젝트 설정에 별도 타임존 값을 두지 않는다(`settings.briefing_timezone` **없음**). 담당자가 교체되면 판정 기준도 자동으로 따라간다.
- 담당자는 카드에서 **"출근 후 처리(defer)"**를 선택해 판단을 미룰 수 있다. 질문자에게는 "확인 대기 중"으로 계속 표시한다. 미루는 기한(`deferred_until`)의 **기본값은 다음 브리핑 시각(`briefing_hour`)**이며, 요청에서 `{until?}`로 지정할 수도 있다(D15).

> 🛟 **알림이 실패해도 질문이 사라지면 안 된다.** 모든 미처리 건은 담당자 인박스(확인 큐)에 남아야 하고, 인박스가 최종 안전망이다.

**[구현 노트]**
- "즉시 알림" = 알림함 레코드 생성 + SSE 이벤트 즉시 발행. 브리핑 대상 건은 브리핑 시각까지 알림 발행을 미루되(`notifications.deliver_after`) **카드는 즉시 큐에 적재**된다(인박스 안전망).
- DND 강등 판정(D2): `held_reason == 'low_confidence'`일 때만 🔴→🟡 강등한다. 강등하더라도 **제거 후 남는 문장이 있을 때만** 가능하다(내보낼 추정 답변 자체가 없으면 강등할 대상이 없다). 강제 🔴 4종은 판정에 들어가지 않고 그대로 🔴이다.
- 🟢 카드는 큐에 적재되지만 **브리핑 조회와 알림 발행 대상에서 제외**된다(룰 1). "맞았다" 2건으로 `recommend_approve`가 되는 순간부터 브리핑에 등장한다.
- 파이프라인 자체가 실패한 질문도 사라지지 않는다. `reason='failed'` 카드를 `answer_id=NULL`, `draft_answer=null`로 만들고 `answer.failed` 알림을 보낸다(D23).

## 7. 교훈 규칙

- 담당자가 답변을 **수정**하면, 원답과 수정답의 차이에서 **교훈 한 줄**을 뽑아 후보(candidate)로 등록한다.
- 교훈은 담당자가 **승인해야만** 이후 답변 생성에 반영된다. 승인 전 교훈은 어디에도 쓰지 않는다.
- 담당자는 교훈을 언제든 삭제할 수 있고, **삭제된 교훈은 다시 생성하지 않는다**.
- 교훈은 프로젝트당 **30개(승인 기준)**까지 유지한다. 초과 시 오래되고 쓰이지 않은 것부터 정리를 **제안**한다. 자동 삭제는 없다.

**[구현 노트]** 삭제 교훈의 `content_hash`를 보관해 동일 내용 후보 재등록을 차단. 승인 교훈은 답변 생성 프롬프트에 주입되며 주입 시 `last_used_at` 갱신.

## 8. 언어 규칙

- 질문자는 **한국어**로 질문하고 한국어로 답을 받는다.
- 지식(공식 Q&A)은 **한국어 확정 원문 + 영어 번역본 쌍**으로 저장한다.
- 담당자에게 넘어가는 질문은 **영어**로 번역하고, 한 번에 답할 수 있게 **배경 → 질문 → 선택지** 순서로 구조화한다.
- 정정 알림은 질문자·담당자 **양쪽 언어**로 보낸다.

**[구현 노트]** 담당자의 수정 입력은 영어(`content_en`) → 서버가 한국어 번역 생성 → 그 한국어가 확정 원문으로 고정된다(이후 재번역 금지, 룰 4). 근거 검색은 질문의 영어 번역문으로 수행한다(지식 원문이 영어이므로).

## 9. 권한과 동시 처리 규칙

- 담당자는 프로젝트당 **1명**, 질문자는 여러 명. 복수 담당자는 다음 버전.
- **담당자는 자기 프로젝트에 질문할 수 없다**(403). 그리고 담당자는 **교체 없이 프로젝트를 떠날 수 없다** — 따라서 **담당자 부재 상태는 발생하지 않는다**(D17). 큐를 받을 사람이 없는 순간이 존재하지 않는다는 뜻이다.
- 질문자는 스스로 프로젝트를 떠날 수 있다. 탈퇴해도 **기존 질문·답변·피드백은 보존**된다(D18).
- 같은 답변에 대해 담당자·질문자 행동이 겹치면 **담당자의 저장이 우선**한다. 담당자 수정 중 질문자의 "달랐다"가 들어오면, 카드 조회 응답에 그 사실(신규 피드백)을 표시하고 저장 시 함께 해소 처리한다.
- 담당자가 퇴근 모드를 꺼도 **처리 중이던 질문은 인박스에 그대로 남는다**. 모드 변경으로 질문이 사라지는 경우는 없어야 한다.

**[구현 노트]**
- 담당자 카드 액션(승인/수정/반려)은 항상 성공(담당자 우선). 카드 처리 시점에 미해소 피드백이 있으면 함께 `resolved` 처리하고 응답에 포함해 프론트가 표시하게 한다.
- 동일 카드 중복 액션은 멱등 차단: 이미 `resolved`면 409 반환 (기능 4.3 "중복 차단").
- 담당자 교체(6.3) 시 미처리 카드·브리핑 항목은 신규 담당자에게 이관된다.
- 담당자 교체는 **한 트랜잭션 안에서 순서를 지켜** 수행한다(D16): ① 구담당자 `role='asker'` 강등 → ② 신담당자 `role='answerer'` 승격 → ③ `projects.answerer_id` 갱신. 역할의 부분 UNIQUE 인덱스는 DEFERRABLE이 아니므로 **단일 UPDATE 스왑은 실패한다.** 경합은 `projects` 행을 `SELECT … FOR UPDATE`로 먼저 잠가 직렬화한다. 구담당자는 삭제되지 않고 질문자로 프로젝트에 남는다.
- 질문자 탈퇴는 멤버십을 `status='left'`로 바꿀 뿐 데이터를 지우지 않는다(D18).
- **프로젝트 삭제는 MVP 범위 밖**이다(D19). 데모 시드 리셋은 API가 아니라 DB 레벨에서 수행한다.

## 10. 지표

운영 판단 기준값. 대시보드(지표 API)에 노출한다. 원천 데이터는 events 테이블.

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| **자동응답률** | 전체 질문 중 🟢+🟡 발행 비율 | 70% 이상 |
| **정정률** | 크로스체크 중 "달랐다" 비율 | 10% 이하 |
| **카드 처리 시간** | 카드 열람부터 담당자 액션까지 30초 내 처리 비율 | 80% 이상 |
| **재질문 즉답률** | `answer.reused / (answer.reused + answer.reuse_missed)` | 95% 이상 |
| **등급별 실측 정확도** | 등급별 `(verified 또는 correct 피드백 ≥1건) / 해당 등급 전체 발행 수` | 표본 30건 이상일 때만 표기 |

**[구현 노트]**
- 원문 룰의 "푸시 수신부터"는 서버에서 관측 불가하므로 **카드 열람(GET 상세) 시각 → 액션 시각**으로 측정한다("30초 검토" 컨셉과 일치). 알림 생성→액션 시간도 보조 지표로 함께 반환.
- **재질문 즉답률의 분모**는 재사용 게이트를 통과한 건(`answer.reused`)과 임계값·2차 게이트에서 걸러진 건(`answer.reuse_missed`)의 합이다(D26). `reuse_missed` 이벤트가 없으면 분모가 만들어지지 않으므로 룰 4의 게이트 탈락 시 반드시 기록한다.
- **등급별 실측 정확도**(D25)는 자동응답률이 은폐하는 실패를 드러내는 지표다. 🟢·🟡·🔴을 합산하지 말고 등급별로 각각 낸다. **표본이 30건 미만이면 숫자 대신 "표본 부족"으로 표기**한다 — 데모 규모에서 나온 비율을 정확도로 읽히게 두지 않는다.
