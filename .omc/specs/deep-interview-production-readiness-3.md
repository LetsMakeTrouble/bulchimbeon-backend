## Goal

단일 서버 전제를 유지한 채 운영에 필요한 세 가지를 해결한다.

1. **동시 요청이 서로를 죽이지 않게 한다** — 진행 중인 답변 생성이 DB 커넥션을 다 쓰면
   새 질문 접수까지 실패한다. 동시 실행에 상한을 두고 그 상한을 풀 크기와 정합시킨다.
2. **누가 얼마를 썼는지 남긴다** — LLM 호출 1회를 1행으로 적재해 계정·프로젝트별 사용량과
   비용을 조회할 수 있게 하고, 재시작에도 사라지지 않는 한도 카운터를 만든다.
3. **예약 작업이 조용히 빠지지 않게 한다** — 기동 직후 1회 실행으로 다운타임 공백을 메우고,
   실행 기록을 남겨 "돌았는지"를 사후에 확인할 수 있게 한다.

## Technical Context

이 저장소에서 직접 확인한 사실이다. 추정이 아니다.

### ① 동시성 — 커넥션 풀 15개가 실질 상한

| 확인 항목 | 값 | 근거 |
|---|---|---|
| 풀 종류 | `AsyncAdaptedQueuePool` | 런타임 조회 |
| `pool_size` / `max_overflow` | **5 / 10 → 최대 15** | `database.py:41` 이 `pool_pre_ping` 만 넘기고 크기를 지정하지 않아 SQLAlchemy 기본값 |
| 세션 보유 구간 | **파이프라인 전 구간** | `answer.py` — `async with session_factory() as db: await _pipeline(db, question_id)` 안에서 LLM 3~4회를 전부 돈다 |
| 파이프라인 실측 소요 | 5~15초 | `eval_questions.py` 최대 15.2초 |
| 동시 실행 제한 장치 | **없음** | `Semaphore` 검색 결과 0건 |
| 접수 경로 | `BackgroundTasks.add_task(run_answer_pipeline, question.id)` | `routers/questions.py:77` |

**결론**: 동시 질문 15건이면 풀이 고갈되고, 신규 질문 접수(`get_db` 의존성)가 같은 풀을
쓰므로 **접수 자체가 막힌다.** 사용자에게는 "요청이 멈춘 것"으로 보인다.

동기 블로킹(파일 파싱)은 이미 `run_in_executor` 로 잘 분리돼 있다 — 그쪽은 문제 없다.

### ② 사용량·비용 — 기록이 없고 500 은 근거가 없다

- `pipeline/quota.py` 는 `{(project_id, UTC날짜): 호출수}` **프로세스 메모리 딕셔너리**다.
  독스트링이 스스로 *"재시작하면 카운터가 0으로 돌아간다 … 상한의 성격이 폭주 방어이지
  회계가 아니다"* 라고 적고 있다.
- 토큰·비용은 **어디에도 저장되지 않는다.** `events.question.graded` 의 `steps` 는 단계
  이름과 소요시간(ms)뿐이다.
- `openai_provider.usage_log()` 는 2026-08-09 에 추가된 **프로세스 메모리 관측 훅**이다.
  DB 적재의 진입점으로 재활용할 수 있다.
- **`daily_llm_call_limit: 500` 의 출처**: 최초 커밋(`113618b`)의 설계 리뷰 문서
  `.omc/specs/deep-dive-bulchimbeon-docs-deep-review.md` 에 등장하며, 기록된 근거는
  *"env 가 아닌 `projects.settings` 로 이동(하드코딩 금지 원칙 일관성)"* 뿐이다.
  **"왜 500인가"는 전 문서·전 커밋 어디에도 없다.** 사용량 추정도 비용 계산도 없다.
- 실측 환산: 질문당 **2.94 호출** · **$0.0098** → 500 호출 ≈ **170 질문/일** ≈
  **$1.7/일** ≈ **$50/월** (프로젝트당).

### ③ 예약 작업 — 큐가 아니라 기동 실행과 기록이 빠졌다

| 잡 | 주기 | 판정 조건 | 소급되나 |
|---|---|---|---|
| 만료 스위퍼 | 10분 | `state='draft'` + `expires_at < now` + 열린 카드 없음 | **된다** (조건 기반) |
| 좀비 회수 | 5분 | `processing` 정체 | **된다** (조건 기반) |
| 브리핑 | 60분 | `briefing_hour` **도달 이후** + 오늘 `briefing_runs` 없음 | **같은 날 안에서는 된다** |

- 세 잡 모두 `coalesce=True, max_instances=1` 이라 밀린 실행이 하나로 합쳐진다.
- 브리핑은 `_claim_run`(`UNIQUE(project_id, run_date)` + ON CONFLICT)으로 **하루 1회가
  제약으로 보장**되고, `_is_catch_up_inside_dnd` 가 "너무 늦은 소급"까지 막는다.
- **빠진 것**: ⑴ 첫 발화가 "기동 + 주기"라 재배포마다 공백 ⑵ 브리핑이 벽시계가 아니라
  기동 시각 기준 ⑶ **실행 기록이 없어 돌았는지 알 수 없다** ⑷ 날짜를 넘긴 다운타임은
  복구 경로가 없다.
